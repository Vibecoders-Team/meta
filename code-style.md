# 🧩 Code style (Python, React/Vite, Solidity)

Единые принципы важнее мелких различий. Мы автоматизируем стиль линтерами и **обязательно** пишем комментарии к нетривиальной логике.

## Общие принципы

- **Читаемость > краткость**. Выбирай понятные имена, избегай магических чисел.
- **Комментарии обязательны** там, где без контекста сложно понять зачем так сделано (алгоритмы, нетривиальные решения, трюки производительности, временные ограничения).
- Один PR - одна осмысленная задача. Меньше «разнородных правок».

## Python (3.11+, uv)

**Инструменты:**
- Форматирование: `ruff format`
- Линтинг: **Ruff**
- Типы: `pyright`
- Тесты: `pytest`

**Быстрый старт:**
```bash
uv venv
uv pip install ruff pytest pyright
# или зафиксировать в pyproject.toml и uv.lock
````

**Стиль:**

* `pyproject.toml` - единая точка конфигурации (Black/Ruff/pytest).
* Имена: `snake_case` для функций/переменных, `PascalCase` для классов, `UPPER_SNAKE_CASE` для констант.
* Импорты: stdlib → сторонние → локальные; группируй, сортируй (Ruff).
* Аннотации типов обязательны в публичных функциях/классах; по возможности - везде.
* Докстроки: формат Google или NumPy, однообразно в проекте.
* Исключения: не глушим `except Exception`; логируем/пробрасываем контекст.

**Комментарии:**

* Короткие - `# почему это нужно`
* Длинные/контекст - в докстроки.
* TODO/FIXME/NOTE с ссылкой на issue.

## Solidity + Hardhat/Anvil

**Инструменты:**

* Форматирование: **Prettier Plugin Solidity** (или `forge fmt`, если используется Foundry)
* Линтинг: **Solhint**
* Тесты: Hardhat (TypeScript) или Foundry

**Стиль:**

* Solidity ≥ версии проекта (зафиксировать в pragma).
OpenZeppelin (Ownable, AccessControl).
* Функции и переменные - понятные имена; видимость явно (`public`, `external`, `internal`, `private`).
* **Checks-Effects-Interactions**; reentrancy guards.
* События (`event`) для важных изменений состояния.
* Требования (`require`) с внятными сообщениями об ошибках.
* Gas-оптимизации - только при доказанной необходимости и с комментариями.

**NatSpec/Комментарии:**

* Публичные функции/контракты - с NatSpec (`@notice`, `@dev`, `@param`, `@return`).
* Любое нетривиальное условие/побочка - комментируем.

---

## Комментарии: стандарты

* Пиши «почему», а не «что» делает очевидный код.
* Подписи к временным решениям: `// TEMP:`, `// WORKAROUND:`.
---

## Проверки перед PR

* Локально прошли: форматирование, линт, тесты.
* Нет «мертвого кода».
* Есть комментарии/докстроки в сложных местах.
