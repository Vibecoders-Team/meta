# 🌿 Ветвление и Git-процесс

Модель: **две стабильные ветки** - `main` и `dev`.  
Обычные **merge-коммиты** (без squash/rebase). Мердж в `main` - **только через PR + code review**.

## Ветки

- `main` - продакшн-состояние, только через проверенные PR.
- `dev` - интеграция фич, стейджинг.

Рабочие ветки создаём от `dev`:
- `feature/<short-name>` - новые фичи
- `fix/<short-name>` - багфиксы
- `chore/<short-name>` - инфраструктура/рутину
- `hotfix/<short-name>` - срочный фикс в прод (от `main`, затем **обязательно** мержим обратно в `dev`)

## Жизненный цикл задачи

1. От `dev` создаём `feature/…`.
2. Коммиты по [Conventional Commits](./commit-message.md).
3. Открываем **PR → dev**. Чекапы CI: линт/тесты/сборка/контракты.
4. Ревью: минимум один апрув. Обычный merge-коммит.
5. Регулярно синхронизируем `dev` (merge `dev` в свою ветку при конфликте).

## Релизы

1. Готовим PR `dev → main` с описанием и ссылками на тикеты.
2. CI генерирует changelog/тег на основе коммитов (SemVer).
3. После мерджа в `main`:
   - автодеплой в прод (с ручным подтверждением, если требуется),
   - **сразу мержим `main` обратно в `dev`** обычным merge-коммитом.

## Политики PR

- В `main` - только через PR + 1+ code review + зелёный CI.
- В `dev` - через PR; авто-мердж запрещён при красном CI.
- Разрешены только **merge-коммиты** (`--no-ff` предпочтительно для явной истории).
- В PR - чек-лист: форматирование, линт, тесты, комментарии в сложных местах.

## Работа с долгоживущими ветками

- Избегаем; лучше дробить на небольшие feature-ветки.
- Если неизбежно - регулярно мержим `dev` внутрь, чтобы не копить конфликты.

## Версионность артефактов и контрактов

- Тэги семантических версий ставятся на `main` (автоматически CI).
- Смарт-контракты: изменения storage-layout → помечаем `BREAKING CHANGE` и документируем миграции.
